# 베타 인증 후 3단계 환영 다이얼로그 설계 — /beta

- 작성일: 2026-10-10
- 상태: 구현 완료 (2026-10-10)
- 대상 페이지: `/beta`
- 목적: 베타 코드 인증 성공 후 환영·실험 목적·향후 기능을 차례로 소개하고, 인증된 사용자만 마지막 버튼으로 홈에 입장시킨다.
- 범위: 베타 페이지의 인증 성공 처리, 전체 화면 3슬라이드 Dialog, 입장 전 서버 인증 확인 및 관련 테스트.
- 제외: 별도 온보딩 라우트, 인증 세션 UUID·2주 만료·LLM 사용량 제한 구현, 분석 SDK 도입.

구현 결과: `BetaWelcomeDialog.tsx`, 인증/입장 mutation hook, 보호된 `/api/beta-auth/enter`를 추가했다. RootLayout Intro와의 충돌은 UI 표시 단계 Context로 방지한다. 서버 단위 테스트, Storybook 브라우저 테스트, 실제 로컬 A/B 인증·홈 입장·인증 만료 테스트로 검증했다. 두 번째 슬라이드는 와인 리스트 촬영·음식 선택·마실 와인 선택의 번호형 안내로 갱신했다.

## 1. 확정 요구사항

1. 베타 코드 인증에 성공하면 곧바로 홈으로 이동하지 않는다.
2. `/beta`에 속한 컴포넌트로 전체 화면 Dialog를 연다.
3. Dialog 내부의 캐러셀로 3개 슬라이드를 탐색한다. 다음/이전 버튼은 없으며 자동 전환은 하지 않는다.
4. 마지막 슬라이드의 버튼 문구는 **첫 번째 마이쏨 시작하기**다.
5. 마지막 버튼은 단순 링크가 아니다. 서버에서 실제 발급된 인증 쿠키를 검증한 후 `/`로 이동한다.
6. 기존 RootLayout IntroDialog와 이번 환영 Dialog는 서로 다른 역할이며 방문 쿠키를 공유하지 않는다.

## 2. 화면 내용

사용자 제공 문구와 의미 있는 줄바꿈을 그대로 사용한다. 작은 화면에서는 overflow 없이 줄바꿈을 추가로 허용한다.

### 슬라이드 1 — 환영

```text
WELCOME TO
MYSOMM FOUNDING 500

마이쏨의 첫 번째 버전에
오신 것을 환영합니다.
```

- 하단: 스와이프·점 인디케이터, `1 / 3` 진행 표시.
- `FOUNDING 500`은 제공된 화면 문구이며 실제 가입자 수나 정원 관리 기능을 의미하지 않는다.

### 슬라이드 2 — 이번 베타의 목적

```text
이번에 함께 확인할 것

1. 와인 리스트를 찍고
2. 함께 먹을 음식을 고르고
3. 지금 마실 와인을 쉽게 고를 수 있는지
함께 확인해주세요.
```

- 하단: 이전·스와이프·점 인디케이터, `2 / 3` 진행 표시.
- 예산 선택 문구는 제거하며, 기존 API 계약과 인증 흐름은 변경하지 않는다.

### 슬라이드 3 — 앞으로의 기능

```text
그리고 앞으로 더해질 것

❤️ 내가 좋아한 와인 기억하기
🍷 나의 와인 취향 알아가기
✨ 사용할수록 나에게 맞는 추천

이번 베타 이후 차례대로 만나볼 수 있어요.
```

- 하단: 스와이프·점 인디케이터, `3 / 3` 진행 표시, **첫 번째 마이쏨 시작하기** 버튼.
- 시작 버튼은 이 슬라이드에만 표시한다.
- 미래 기능은 안내 문구이며 해당 기능을 이번 작업에서 구현하지 않는다.

## 3. 사용자 흐름 및 상태

```text
코드 입력 → 인증 요청
               ├─ 실패 → 기존 오류 안내, Dialog 표시 안 함
               └─ 성공 → 쿠키 발급 + Dialog 1
                                        ↓ 스와이프 / 점 선택
                                     Dialog 2
                                        ↓ 스와이프 / 점 선택
                                     Dialog 3
                                        ↓ 시작 버튼
                                서버 인증 확인
                                  ├─ 유효 → 홈(/)
                                  ├─ 만료/없음 → 재인증 안내
                                  └─ 통신 오류 → 3페이지 유지, 재시도
```

- 로컬 UI 단계: `code-entry`, `onboarding`, `entering`, `entry-error` 등으로 구분한다.
- 현재 슬라이드 인덱스는 0~2이며, 스와이프·점 선택·방향키 이동은 범위를 벗어나지 않는다.
- 인증 Mutation 성공 응답의 `{ ok: true }`를 확인한 뒤에만 첫 슬라이드를 연다.
- 인증 성공 시 코드 입력값을 비우고 제출을 다시 실행하지 않는다.
- 인증 성공 직후의 `router.replace('/')`와 `router.refresh()`는 제거한다.
- 온보딩 중에는 페이지 refresh/navigation을 자동 실행하지 않는다. 토큰 발급 후 `/beta`를 다시 요청하면 기존 미들웨어가 인증된 사용자를 홈으로 보내므로 화면이 조기에 종료될 수 있다.
- 시작 처리 중 스와이프·점 선택 및 시작 버튼의 중복 실행을 막고 스피너와 접근 가능한 진행 상태를 제공한다.

## 4. 컴포넌트 구성과 책임

```text
web/src/app/
├─ beta/page.tsx                              # Server Component 유지
├─ feature/beta-access/
│  ├─ ui/BetaAccessForm.tsx                    # 인증 결과와 Dialog 조합
│  ├─ ui/BetaWelcomeDialog.tsx                 # 3슬라이드 controlled Dialog
│  ├─ ui/BetaWelcomeDialog.stories.tsx         # 화면·이동·입장 상태 검증
│  └─ api/use-beta-access.ts                  # 인증/입장 Mutation
├─ shared/ui/molecule/dialog.tsx              # fullscreen 공통 Dialog 사용
└─ api/beta-auth/
   ├─ route.ts                               # 기존 코드 인증·쿠키 발급
   └─ enter/route.ts                          # 신규 입장 전 인증 검증
```

- `page.tsx`는 Server Component를 유지한다.
- `BetaAccessForm`은 인증 성공을 Dialog 열기로 연결한다. 기존 입력 UI와 오류 표시를 재사용한다.
- `BetaWelcomeDialog`는 정적 문구와 슬라이드 UI, 캐러셀 탐색·시작 이벤트를 담당한다. 인증 토큰을 props로 받거나 직접 읽지 않는다.
- 인증 및 입장 요청은 same-origin BFF API와 TanStack Query Mutation으로 분리한다. Mutation 응답 전체를 Zustand나 로컬 state에 복제하지 않는다.
- 슬라이드·Dialog open은 단일 기능의 로컬 상태이며 전역 store를 추가하지 않는다.
- 기존 API 응답 `{ ok: true }`는 그대로 유지한다. JWT 원문을 응답 DTO에 추가하지 않는다.

## 5. UI·공통 컴포넌트·접근성

- 기존 `shared/ui/molecule/Dialog`와 `DialogContent fullscreen`, 공통 atom Button·LoadingSpinner를 사용한다. feature에서 shadcn을 직접 import하지 않는다.
- 화면 전체를 덮고 내부 콘텐츠는 모바일 중심 폭으로 제한한다. 작은 높이에서는 콘텐츠 영역 스크롤과 하단 버튼 접근을 보장한다.
- 현재 primary 색·타이포그래피·간격 체계를 따른다. 구체적인 배경/세부 디자인은 제공 문구를 기준으로 구현 전에 정리한다.
- 기존 저장소에는 이번 온보딩 전용 시안이 없으므로 새로운 디자인 파일이 있다고 가정하지 않는다.
- 이번 Dialog는 1초 자동 닫기 Intro와 달리 사용자가 읽고 진행하는 화면이다. 자동 닫기/자동 슬라이드를 적용하지 않는다.
- Dialog 내부를 CSS scroll-snap 캐러셀로 구성한다. 다음/이전 버튼 없이 모바일 스와이프·하단 점 클릭·캐러셀 영역 방향키로 탐색한다. 기존 추천 캐러셀과 같은 브라우저 기본 스크롤 방식이며 새 라이브러리나 자동 재생은 추가하지 않는다.
- 상태와 입장 비동기 처리가 연결되므로 작은 Client Component의 슬라이드 상태를 사용한다. CSS는 전환 표현을 담당한다.
- 각 슬라이드 제목과 현재 순서를 접근 가능하게 제공한다. 스와이프 중 포커스를 강제로 이동하지 않는다. 비활성 슬라이드는 inert로 포커스 진입을 막고, 캐러셀 영역에 키보드 포커스를 제공한다.
- Dialog primitive의 포커스 트랩과 배경 스크롤 차단을 사용한다. 키보드·스크린리더·reduced-motion을 검증한다.
- 일반 닫기 버튼·바깥 클릭·ESC로 온보딩을 건너뛰지는 않는다. 인증 오류에서 제공하는 명시적인 재인증 동작은 허용한다.
- 공통 Dialog는 현재 기본 닫기 버튼을 포함하므로, existing `closeClassName` 등 공개 props로 숨기고 escape/outside 이벤트를 처리한다. 다른 Dialog의 기본 동작을 전역 변경하지 않는다.

## 6. 마지막 버튼의 서버 인증 검증

### 요청 계약

- 신규 endpoint: `POST /api/beta-auth/enter`.
- 요청: 브라우저가 HttpOnly access·refresh 쿠키를 same-origin으로 자동 전송한다. 토큰이나 목적지를 body로 받지 않는다.
- 성공: `200 { ok: true }`, `Cache-Control: private, no-store`.
- 미인증/만료/잘못된 서명: `401`과 안전한 재인증 메시지.
- 금지된 Origin: `403`. 잘못된 method는 허용하지 않는다.
- 서버 장애: 안전한 `5xx` 메시지. 내부 오류·JWT·베타 코드를 반환하거나 로깅하지 않는다.

### 검증 책임

1. `/api/beta-auth/enter`는 미들웨어의 공개 API 목록에 추가하지 않는다. 정확한 기존 `/api/beta-auth`만 코드 인증용 공개 endpoint다.
2. 미들웨어의 기존 access 검증·refresh 갱신을 사용한다. 유효한 refresh로 access를 갱신한 경우 쿠키를 요청 헤더에 전달하는 기존 경로를 유지한다.
3. Route Handler에서도 access JWT의 서명·issuer·audience·type·만료를 검증한다. 쿠키 존재 여부만 검사하지 않는다.
4. 입장 성공 응답을 확인한 뒤에만 홈으로 이동한다. 최종 홈 요청도 기존 미들웨어에서 다시 보호한다.

HttpOnly 쿠키는 JavaScript로 읽지 않는다. 로컬 `authenticated=true`나 Dialog open 상태만으로 입장 권한을 판단하지 않는다. 토큰이 있다는 사용자의 주장이나 임의 UUID는 인증 근거가 아니다.

### 홈 이동

기본안은 검증 성공 후 `window.location.replace('/')`로 새 문서 요청을 보내는 것이다. 인증 전 캐시된 홈/베타 RSC 결과를 재사용하지 않고 서버 쿠키를 확실히 반영하며, 뒤로가기 기록에 온보딩을 추가하지 않는다. 페이지 내 슬라이드 탐색에는 라우팅이 없다.

SPA 이동을 유지하려면 `router.replace('/')`와 인증 이후 Router Cache 갱신 순서를 실제 브라우저에서 검증해야 한다. 어떤 방식이든 서버 인증 확인보다 먼저 이동하지 않는다.

## 7. 실패 처리와 재인증

- 인증 실패: 기존 입력 폼의 오류를 표시하고 Dialog를 열지 않는다.
- 인증 응답은 성공했으나 쿠키가 저장되지 않음/차단됨: 마지막 입장 요청은 401로 실패하며 홈으로 이동하지 않는다.
- access 만료 + 유효한 refresh: 기존 미들웨어 갱신 후 입장할 수 있다.
- 둘 다 만료되거나 쿠키 삭제: Dialog에 재인증 안내를 표시하고 명시적인 코드 재입력 버튼으로 폼으로 돌아간다. 포커스를 코드 입력에 복원한다.
- 네트워크/5xx: 3페이지에 머물며 재시도 버튼을 제공한다. 자동 인증 재발급이나 반복 이동을 하지 않는다.
- 요청은 timeout을 적용하고 인증/입장 자동 재시도는 하지 않는다. 중복 클릭을 방지한다.
- A/B 두 베타 코드 모두 같은 온보딩을 표시하며 토큰의 variant를 유지한다. 이후 추천 화면 분기는 기존 정책을 따른다.

## 8. 기존 전역 Intro 및 재접속 정책

- RootLayout IntroDialog: 브라우저 첫 방문의 짧은 브랜드 소개, 기존 24시간 방문 쿠키 정책 유지.
- BetaWelcomeDialog: `/beta`에서 코드 인증 성공 후 열리는 읽기 기반 3단계 안내. Intro 쿠키와 무관하다.
- 두 Dialog가 동시에 열리지 않도록 전역 Intro 표시 중 인증 폼 상호작용이 차단되는 기존 모달 동작을 확인한다. 느린 상태 조회와 키보드 제출 등 비정상 순서에서도 겹치지 않도록 구현 시 표시 조정을 검토한다.
- 홈 이동 시 Intro 쿠키가 저장되어 있으면 재표시하지 않는다. 쿠키 저장 실패 등의 경우 전역 정책에 따라 Intro가 다시 표시될 수 있다.
- 이미 유효한 인증을 가지고 `/beta`를 새로 여는 사용자는 기존 미들웨어에 따라 홈으로 이동한다. 기존 인증 사용자에게 온보딩을 강제로 다시 보여주지는 않는다.
- 인증 직후 온보딩 도중 새로고침해도 현재 정책상 홈으로 이동할 수 있다. 이 설계는 인증된 입장을 보장하지만, 3장 모두를 읽었음을 서버에서 증명하는 기능은 아니다.
- 새로고침/직접 홈 접근까지 온보딩 완료를 의무화하려면 별도 서버 완료 상태와 라우팅 정책이 필요하다. 이번 요청에서는 그 범위를 임의로 추가하지 않는다.

## 9. 토큰 정책 범위

현재 access 15분, refresh 7일 정책을 유지한다. 앞서 논의한 2주 auth UUID와 LLM 호출 제한은 별도 인증/백엔드 설계이며 이번 온보딩 작업에 포함하지 않는다. 기존 token claim과 API 계약을 임의로 확장하지 않는다.

## 10. 구현·검증 순서

1. 문구와 현재 서비스 흐름의 정합성을 확인한다.
2. fullscreen 공통 Dialog와 버튼으로 3슬라이드 View 및 Storybook을 작성한다.
3. 보호된 enter Route Handler와 인증·refresh·Origin 테스트를 작성한다.
4. 코드 인증 로직을 Mutation으로 분리하고 성공 시 즉시 이동 대신 Dialog를 연다.
5. 마지막 버튼을 서버 검증·로딩·오류·재인증·홈 이동에 연결한다.
6. 전역 Intro와 중첩/포커스/페이지 전환을 검증한다.
7. 구현 후 `/beta` 개발 문서에 실제 구성과 계약을 반영한다.

| A/B 인증 성공 | 즉시 이동 없음, 1페이지 표시 |
| 캐러셀 탐색 | 스와이프·점 클릭·방향키, 시작 버튼은 3페이지에만 표시 |
| 자동 대기·ESC·바깥 클릭 | 자동 이동/닫기 없음 |
| 유효한 토큰으로 시작 | enter 검증 성공 후 `/` 요청 |
| access 만료, refresh 유효 | 갱신 후 입장, variant 유지 |
| 토큰 없음·위조·모두 만료 | 입장 거부, 재인증 안내 |
| 쿠키 저장 차단 | 성공 UI만으로 홈 이동하지 않음 |
| 통신 오류·중복 클릭 | 3페이지 유지, 안전한 재시도, 중복 요청 방지 |
| 인증 직후 refresh | 온보딩 중 실행하지 않음 |
| 이미 인증된 `/beta` 방문 | 기존 홈 리다이렉트 유지 |
| 모바일·키보드·reduced-motion | 전체 내용과 버튼 접근, 포커스/스크롤 정상 |
| 전역 Intro 동시 표시 가능성 | 모달 중첩·포커스 충돌 없음 |
